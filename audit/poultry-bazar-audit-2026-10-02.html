Poultry BAZAR audit

Covers UI/UX, desktop vs mobile, security, features, SEO and performance. Based on the production frontend source at commit e41b803 (27 Sep 2026), rendered and tested in Chromium.

The product idea is sound and the mobile experience is decent. The site does work worse on desktop, and the cause is clear: it is a phone layout stretched to full screen width. On a 1366px laptop, the home page shows zero listings above the fold. The more serious problems are elsewhere, though: one possible account-takeover path that needs checking today, listings that search engines can't index, and missing features (price, buyer requests, alerts) that matter more to the business than desktop polish.

How this was tested, and what wasn't

  • This environment's network policy blocks poultrybazarbd.com, the API at poultry-bazar-api.onrender.com and dl.poultrybazarbd.com. I could not load the live site or reach the backend.
  • The site's full source is public at github.com/habibrahman0623/poultry-bazar-web: the marketplace, the admin panel, and the about, privacy and delete-account pages. It's a static site on GitHub Pages. I read every file.
  • I served that exact code locally, mocked the API with realistic data, and measured it at 390px (phone), 1366px (laptop) and 1920px (desktop). The layout numbers below come from the real CSS. Images in the screenshots are flat-color placeholders.
  • I did not use your login. Without API access there was nothing to log into. Anything that depends on backend behavior is marked "verify" and listed in a test checklist at the end. You also pasted a live password into a chat. Change it.

Fix these first

  1. Check that production never returns devOtp. The frontend auto-fills an OTP sent back by the API in "development mode". If the live backend still does this, anyone can reset the password of any account using only its phone number. That's a 5-minute test (see Security).
  2. Add rate limits and a CAPTCHA on OTP sending. Registration and password-reset requests send an SMS to any number with no visible protection. That lets attackers drain your SMS credit (SMS pumping).
  3. Put the app in a centered container on desktop. About 40 lines of CSS fix most of the desktop complaint (snippet below).
  4. Accept Bengali digits. Typing ০১৭১১০০০০০০ as a phone number or ১০০ as a bird count fails today. Many of your users type on Bangla keyboards.
  5. Move listings off hash URLs. /#/ads/CODE is invisible to Google. Every listing you have brings in zero search traffic.

Desktop vs mobile: why desktop feels worse

You were right. The whole marketplace (index.html) is a single mobile layout with no maximum width. Every block is width: 100%, and several have fixed aspect ratios, so their height grows with the screen width. On a phone that looks good. On a laptop, the banner and photos grow until the actual listings are pushed off screen.

Fix (drop-in CSS, about 40 lines)

This doesn't need a redesign. Wrap the views in a centered container and cap the large media:

@media (min-width: 900px) {
  body { background: #e9ece8; }
  .view, .notice-bar { max-width: 1180px; margin-inline: auto; }
  .view { background: var(--bg); min-height: calc(100vh - 62px); }
  header.topbar { padding-inline: max(16px, calc((100vw - 1180px) / 2)); }

  /* Banner: short strip, not a wall */
  .banner-wrap { aspect-ratio: auto; height: 260px; }

  /* Listings: 4–5 columns of sane size */
  .ad-grid { grid-template-columns: repeat(auto-fill, minmax(220px, 1fr)); }
  .ad-card:hover { box-shadow: 0 4px 16px rgba(0,0,0,.08); transform: translateY(-2px); }

  /* Detail: photo left, info + call right */
  #detailContent { display: grid; grid-template-columns: 1.2fr 1fr; gap: 24px; padding: 20px; }
  .carousel { aspect-ratio: 4/3; border-radius: 14px; }

  /* Forms and wizard stay narrow */
  .wizard-body, .filter-form, #view-feedback > div { max-width: 640px; margin-inline: auto; }

  /* Sell button: a normal button, not a full-width bar */
  .sell-bar { left: auto; right: max(24px, calc((100vw - 1180px) / 2)); bottom: 24px;
              border: none; background: none; padding: 0; width: 280px; }
  body { padding-bottom: 0 !important; }
}

Also change the health cards and category circles to <button>, and give the icon-only buttons (☰ 👤 ← 👁) an aria-label.

Don't overspend on desktop. Your sellers are farmers and your buyers are traders (পাইকার), almost all on Android phones and often inside Facebook's in-app browser. Apply the CSS above, then put the effort into the items below. Check your analytics for the real desktop share before doing more. The admin panel records active devices, but not device type. Add that.

Security

The frontend's own code is reasonably careful. User text is escaped consistently, which blocks most XSS. The real risks sit at the boundary with the backend, and in how tokens are stored. Items marked "verify" depend on backend behavior I couldn't reach.

Critical
verify

Development OTP bypass may be live

The OTP screen reads devOtp from the API response and pre-fills it, with a "ডেভেলপমেন্ট মোড" note. If the production backend still returns devOtp, OTP proves nothing. An attacker calls /auth/password-reset/start with a victim's number, reads the code from the response, sets a new password, and owns the account. That includes admin accounts.

Test: request a password reset for your own number and look at the JSON response in browser DevTools → Network. If it contains devOtp, turn it off in production immediately and remove the auto-fill code.

index.html:1308-1310

High
verify

SMS pumping / OTP abuse

/auth/registration/start and /auth/password-reset/start send an SMS to any valid BD number without login. Without per-number and per-IP limits, a script can send thousands of SMS on your account, or flood one person's phone. The 6-digit OTP also needs a cap on attempts: 1,000,000 codes is brute-forceable without lockout.

Fix: limit to about 3 sends per number per hour and per IP, add a CAPTCHA (Cloudflare Turnstile is free), lock after 5 wrong OTPs, and expire codes after 5 minutes.

High

Admin and user tokens in localStorage, on the same origin

Access and refresh tokens are stored in localStorage (pb_access, pb_refresh, pb_admin_access, pb_admin_refresh). The admin panel lives at /admin/ on the same origin as the public marketplace. Any single XSS bug, or a compromised Google Fonts response, can read the admin's refresh token and keep admin access. There is no Content-Security-Policy.

Fix: move admin to its own subdomain (e.g. admin.poultrybazarbd.com). Add a CSP <meta> tag limiting scripts to 'self' and connect-src to the API and storage hosts. Long-term, put refresh tokens in an HttpOnly cookie.

index.html:708-719 · admin/index.html:402-415

High

Every seller's phone number is publicly scrapeable

GET /ads and /ads/{code} return the seller's name and mobile number without login. Ad codes are a 1-2 character category prefix plus, most likely, a running number, so they are easy to enumerate. Anyone can harvest every seller's number for scam calls; fake-buyer and advance-payment scams are common in BD livestock trade. Your privacy policy says numbers are public "by design", which is legal cover, not protection.

Fix: keep listings public, but return the number only after login or a CAPTCHA tap ("নম্বর দেখুন"), and rate-limit reveals per user.

Medium
verify

Admin role is only checked in the browser

The admin login rejects non-admins with if (data.user.role !== 'ADMIN') in JavaScript. That's just a UI check. Every /admin/* endpoint must reject non-admin tokens on the server.

Test: log in as a normal user, copy pb_access from localStorage, and call GET /api/v1/admin/metrics with it. Anything other than 403 is a critical hole.

admin/index.html:504

Medium

Admin logout doesn't revoke the session

The public app calls /auth/logout on logout. The admin panel only clears localStorage, so the admin refresh token stays valid on the server.

admin/index.html:515-517

Medium

Admin panel can be framed (clickjacking)

GitHub Pages can't send X-Frame-Options or frame-ancestors headers, and neither works from a meta tag. A malicious page could frame /admin/ and trick a logged-in admin into clicking "delete".

Fix: host admin behind Cloudflare (free) and set the header, or at minimum add a frame-busting script.

Medium

Photo uploads aren't checked

The upload PUT to storage never checks res.ok, so a failed upload still creates the ad with broken images. The presign request sends the file type and size from the client. The server must enforce limits (e.g. 5 MB, JPEG/PNG/WebP only) and confirm each object exists before saving the ad.

index.html:1556-1560 · admin/index.html:944

Low

Smaller items

Change-password and admin password reset use prompt(), which shows passwords in plain text and doesn't work in some in-app browsers. The tel: href and several admin fields (role, status, reason) are inserted without escaping. They're server-controlled today, but should be escaped anyway. The anonymous feedback endpoint has no CAPTCHA, so it's a spam target. The APK is sideloaded, with no checksum and the version hard-coded in 6 places.

The bigger gaps

These matter more than any bug above. Without them, the product is a listings board, not a marketplace:

  • No asking price. Price is the first thing a buyer wants to know. Today every listing forces a phone call just to find it out. Daily rates change, so make the field optional ("দরদাম সাপেক্ষে" allowed), but offer it.
  • You're collecting a price index and not showing it. Every "mark as sold" records soldPricePerKg with category and district. A public daily board ("আজকের ব্রয়লার রেট — গাজীপুর ১৭২৳/কেজি") is something farmers and traders check every day. It would be your strongest retention and SEO asset, and you already have the data.
  • Only sellers can post. Traders who need 2,000 broilers by Friday can't post a "কিনতে চাই" (want to buy) request. The demand side is half the market.
  • No alerts. A trader can't say "notify me about broiler-ready ads in Gazipur". They have to check manually, and most won't.
  • No trust signals. No verified-seller badge, seller history ("12 sold"), or ratings. In a market with scams, trust drives response rates.
  • Too much friction for sellers. 5 mandatory photos, no draft, no repost. Every extra step costs listings, and listings are what bring buyers. Make 1-2 photos required and 5 optional.

UI, UX and accessibility

  • Visual identity is good. The green and orange brand, Bangla-first copy, large tap targets and simple 4-step wizard suit the audience. Keep them.
  • Bengali digits are rejected everywhere. <input type="number"> drops ১০০ (I confirmed the value comes back empty), and the phone check fails ০১৭…. Convert ০-৯ to 0-9 before validating, and use inputmode="numeric" on text inputs instead of type="number".
  • Browser dialogs (alert, prompt, confirm) handle sold price, change password, delete confirmation and errors. They look broken on mobile and are unreliable inside Facebook's in-app browser, where many of your visitors arrive. Replace them with in-page sheets.
  • Back buttons ignore history. Each "←" goes to a fixed route. Browsing ads → opening one → back sends you to the top of Home and loses your scroll position. Use history.back() when there is history.
  • Errors are silent. If the feed, categories or districts fail to load, the user sees an empty page with no message and no retry button. In the sell wizard, a failed district load throws an unhandled error.
  • Accessibility. Icon buttons have no labels. Form <label>s aren't linked to their inputs. Ad images have empty alt. The blinking "App" label and the ticker never stop (WCAG 2.2.2). The report link (#888 on #F4F5F3) and search placeholder (#7a8079 on white) fail contrast. 11.5px text on cards is small for older farmers.
  • Layout shift. The notice bar and category strip appear after loading and push content down, which feels jumpy on slow connections.
  • No custom 404. Unknown paths show GitHub's generic 404 page.

SEO

Critical

Listings can't be indexed

Every ad lives at /#/ads/CODE. Search engines ignore everything after #, so they see exactly one page, the home page. The listings are fetched by JavaScript from a separate API. For a marketplace, listings are the SEO, and you currently have none.

Fix: use real paths (/ads/<code>) and render them on a server or pre-build them. At minimum, have the API serve a small HTML page per ad with title, description and Open Graph tags, and generate a sitemap.xml from active ads.

High

No Open Graph tags, so links shared on Facebook and WhatsApp show no preview

In Bangladesh, Facebook groups and WhatsApp are where poultry gets sold. A shared Poultry BAZAR link currently shows no image and no description. Add og:title, og:description and og:image (1200×630) to every page. Once ads have real URLs, give each ad its own preview.

Medium

Weak home page signals

The title is only "Poultry BAZAR", with no keywords; use something like "Poultry BAZAR — মুরগী কেনা-বেচার অনলাইন বাজার | ব্রয়লার, সোনালী, লেয়ার". There's no <h1> on the home page, no canonical tag, no robots.txt, no sitemap.xml, and no structured data (Organization, and Product/Offer per ad). The favicon is the wide 712×169 logo squeezed into a square. Add a square icon, apple-touch-icon and a web manifest.

Low

What's already right

lang="bn" is set, the description is in Bangla, Search Console is verified, the old /browse/ path redirects with a canonical, and /about/ has a good title and description.

Performance and reliability

  • Hosting on onrender.com. If the API is on Render's free tier, it sleeps after 15 minutes idle, and the first visitor waits 30-60 seconds with a spinner. Googlebot gets an empty page. Check the plan. If it's free, upgrade, or ping it every 10 minutes as a stopgap.
  • Photos are uploaded at full size, one after another, with no progress shown. Resize to about 1600px JPEG in the browser before upload; that cuts upload size 5-10× on mobile data.
  • Positive: one HTML file, no framework, inline CSS/JS, lazy-loaded card images, and a 19 KB logo. The frontend itself is light.
  • Small items: the notice ticker runs a JavaScript timer 25 times a second instead of a CSS animation. URL.createObjectURL previews are never released. The Google Font blocks first render.
